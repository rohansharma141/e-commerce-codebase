# ADR-0010: Storefront sells separately from the API

**Status:** Accepted
**Date:** 2026-06-01

## Context

The API MVP shipped first (build priority 1–6) as a complete product. The Next.js storefront added later (priority 7) had to remain optional — some customers will only buy the API and front it with their own UI, others want the bundled storefront.

That's an architectural constraint, not a marketing tagline. If the storefront silently grew dependencies on internal module contracts, on the in-process event bus, or on shared backend libs, "sell separately" would only be true in theory. Every refactor of the api's internal contracts would risk breaking the storefront, and customers buying API-only would receive code that references types and packages they don't need.

## Decision

The storefront imports ONLY from `packages/api-client/`. Never from `packages/modules/*` (a module's contracts or src) and never from `packages/shared/*` (the backend's shared libs).

Enforced two ways:

1. **ESLint `@nx/enforce-module-boundaries`.** A constraint in `.eslintrc.cjs` says `scope:storefront` may only depend on `scope:api-client`. `scope:api-client` itself depends on nothing in the workspace. Both tags are declared in each project's `project.json`. A violation is a build failure.

2. **TypeScript path aliases.** `tsconfig.base.json` exposes `@platform/api-client` to the storefront. Other `@platform/*` aliases exist but the storefront's tsconfig + ESLint don't permit them.

`packages/api-client/` is the public contract surface. It has two kinds of types:

- **GraphQL** — generated by `@graphql-codegen/client-preset` from a saved copy of the api's SDL (`packages/api-client/schema.graphql`). Refreshed with `pnpm nx run api-client:fetch-schema` while the api is up, then `pnpm codegen`. Generated documents are committed so the storefront builds without needing the api running.
- **REST** — hand-mirrored in `packages/api-client/src/rest.ts`. Same shape as the api's internal module contracts (Cart, Order, ComputedTotals, etc.) but deliberately duplicated.

The hand-mirror is the controversial part — it could be auto-generated. We chose manual today because:

- @nestjs/swagger ships, but our DTOs are TS interfaces, not Nest classes with `@ApiProperty`. The generated OpenAPI schemas are empty for request/response bodies. `openapi-typescript` would produce `unknown` types.
- Promoting every DTO to a class with @ApiProperty decorators is a real task. It's the right next step — `packages/api-client/src/rest.ts` carries a comment pointing at that work. Once it lands, the hand-mirror retires.

## Consequences

- The storefront can be packaged, sold, and deployed without shipping any backend source code. The artifact is just a Next.js build + the api-client dist.
- API-only customers receive only `apps/api/` and `packages/{shared,modules}/`. No storefront, no Next.js, no React, no Tailwind in the bundle.
- Refactoring an internal module contract (say, renaming a field on the orders module's internal `Order` type) does NOT break the storefront automatically. The storefront sees the api-client types. The next codegen run surfaces drift. CI catches mismatches.
- The storefront cannot "secretly" implement business logic. Every capability the storefront uses must be reachable through the api's public schema. If we want a new feature (say, related products), the api gets the new query first — the storefront can never invent it client-side by joining endpoints. This is the most load-bearing consequence: the rule shapes how we think about features.
- Hand-mirrored REST types are duplication. The mitigation is that they live in one file, are tested against the api by the full purchase-flow integration (carts, checkout, orders), and have a clear path to auto-generation.

## Alternatives considered

**Storefront imports `@platform/modules/*/contracts`.** Rejected. Modules' contracts packages are the api's INTERNAL contract surface — they evolve at the speed of the api's refactoring needs. Externalising them as the storefront's API would couple the storefront to internal churn. The api-client layer is the cushion.

**Auto-generate REST types from @nestjs/swagger output today.** Rejected because the swagger output today doesn't carry body schemas (interfaces, not class DTOs). The mirror is honest; the fix is to land @ApiProperty on the DTOs and then regenerate.

**Drop the constraint and let the storefront import freely.** Rejected — the rule is the product. Without it the "sell separately" claim is theatre.
